YOUR PDF KNOWS WHO MADE IT, TWICE

Send a CV, a quote, a rental application, a court filing. It is a PDF, so it feels finished and inert, like paper. It is not. A PDF is a database, and it usually knows more about its own history than you would put in the covering email.

Two places, the same name

Every PDF has a document information dictionary. Title, Author, Subject, Keywords, Creator, Producer, plus creation and modification timestamps. Author is often your operating system account name, which is often your full name. Creator names the application you actually wrote it in, which quietly tells the recipient whether that "professionally prepared report" came out of Word, Canva or a phone scanner.

Then there is usually an XMP packet: the same information again in XML, and often more of it. Editing history. The software chain the file passed through. On some office exports, a stored account name that no longer matches anything you would recognise.

Both get read and both get cleared, because clearing one and leaving the other is the kind of half-fix that makes people trust a tool they should not.

The identifier nobody mentions

PDFs also carry a file identifier in the trailer: a pair of hashes. The first half is meant to stay stable across saves, so a viewer can tell that two files are versions of one document.

Which means it also links two files you did not want linked. Send a quote to one client and a near-identical quote to another, and the shared identifier says they came from the same original. MetaStrip reports it and can zero it, and if you drop several documents in at once it will tell you which of them share one.

Cleaning a PDF without breaking it

This is the part that makes most tools re-render the whole document, which is how you get a fuzzy scan out of a crisp vector file.

A PDF has a cross-reference table listing the exact byte offset of every object in the file. Delete one byte anywhere earlier and every offset after it is wrong. Some readers repair that silently, others refuse the file.

So nothing moves. A literal string value is overwritten with spaces inside its own parentheses, a hex string becomes zeros so it stays valid hex, and an XMP packet is blanked where it sits. Same length, same offsets, same table, same pages. Nothing is re-rendered and no content stream is touched.

Checked against a real file: a PDF printed by Chrome came out the same length, with not one byte inside a content stream changed, every cross-reference offset still landing on an object, and macOS's own PDF engine rendering it to pixels identical to the original.

The one case that gets declined

If a PDF is encrypted, its strings are ciphertext. Blanking them would corrupt the file without being able to tell you what was in there, so MetaStrip says so and stops. Remove the password first, then clean it. A tool that quietly mangles an encrypted file to look busy is worse than one that admits the limit.
